## 1. Objective
Implement the selected identity path with revocable sessions, MFA and safe recovery.
## 2. Business Context
Only verified accountable humans should access bids or approve high-risk operations.
## 3. Scope
Approved provider/password flow, verification, login/logout, MFA enrollment/challenge/recovery, step-up, session list/revoke and /me identity bootstrap.
## 4. Out of Scope
Tenant role grants and enterprise SCIM. Password and Google identity paths are both approved; neither confers tenant authority.
## 5. Technical Requirements
Hashed opaque tokens, secure cookie/CSRF, rotation and auth epoch; approved Argon2id if applicable; generic enumeration-resistant errors; bounded abuse controls; single-use challenges; encrypted factor material and safe security audit.
## 6. Proposed Implementation Approach
Implement identity ports and challenge transitions; integrate controlled notification/provider adapter; enforce request controls; expose approved contracts; add adversarial browser/integration tests.
## 7. Dependencies
[Control DB](../database/BID-DB-002.md), [command boundary](../backend/BID-BE-001.md), [API](../backend_contracts/BID-API-002.md), [notifications](../integrations/BID-INT-001.md), [threat model](../security/BID-SEC-001.md).
## 8. Acceptance Criteria
- Given successful login/MFA, then prior session fixation token is unusable.
- Given concurrent recovery token reuse, then exactly one consumes it and affected sessions revoke.
- Given cross-origin cookie write, then CSRF protection rejects it.
## 9. Testing Requirements
Identity integration/E2E, expiry/replay/enumeration/throttling, cookie assertions and redacted logs.
## 10. Definition of Done
Selected identity flow works with real test dependencies and all negative contract/security evidence.

### Current-account session inventory preparation

`GET /v1/auth/sessions` now lists at most 100 active, unrevoked, unexpired sessions matching the account's current auth epoch. It requires the authenticated session plus exact approved HTTPS Origin and matching session-bound CSRF cookie, marks the current session and returns creation/last-seen/idle/absolute expiry and rotation predecessor IDs only. It exposes no token/CSRF hashes, IP, user agent, inferred device or location. Current-session logout remains available; revoke-other and revoke-all remain false with `SESSION_ADMINISTRATION_POLICY_NOT_CONFIGURED`. Status: **IMPLEMENTED_NOT_VERIFIED**.

BID-ADR-022 is approved and implemented in source as **IMPLEMENTED_NOT_VERIFIED**. Control migration `00012` stores hash-only revoke-one command evidence. The composed owner-only routes revoke one other session with concealed idempotent semantics or revoke every active session including the caller by advancing auth epoch, with 15-minute freshness, exact Origin/CSRF, bounded counts, minimal audit/outbox evidence and no-touch failure handling. Revoke-all clears both cookies and issues no replacement. No administrator authority or device/IP/user-agent/location collection is added. Live concurrency, migration and browser acceptance remain deferred.

### Password recovery posture preparation

`GET /v1/auth/recovery/preparation` now gives the authenticated current account a private/no-store view of verified-email, disabled-account, password-credential and linked-Google facts. It requires exact approved HTTPS Origin and matching session-bound CSRF cookie and exposes no email value, credential version, PHC, provider subject or unauthenticated account lookup. It always keeps recovery request/reset unavailable and reports token, delivery and session-effect policy blockers. No recovery challenge, email, password mutation or session revocation is implemented. Status: **IMPLEMENTED_NOT_VERIFIED**.

### Approved pilot password-recovery core

Control migration `00010_password_recovery.sql` and provider-neutral application/persistence code now implement the approved independent recovery invariants: 32 random bytes, SHA-256 at rest, 30-minute expiry, one active challenge per password user, resend invalidation, atomic single use, verified/non-disabled password identities only, no Google-only password creation, Argon2id validation/hash before reset, credential-version and auth-epoch advancement, all-session revocation and content-free audits. SMTP delivery uses authenticated STARTTLS and delivery failures are intentionally non-distinguishing. The subsequently approved exact limits are implemented with recovery-domain-separated HMAC scopes and atomic Redis enforcement: identity 3/hour, network 10/hour and 15-minute denial with `Retry-After: 900`. Strict exact-Origin request/reset handlers are conditionally composed only when explicit SMTP registration configuration exists. Unknown, malformed, Google-only and ambiguous-delivery request outcomes are generic `202`; reset success revokes all sessions and returns `204`. Status: **IMPLEMENTED_NOT_VERIFIED**.

### MFA and step-up readiness preparation

`GET /v1/auth/mfa/preparation` now provides a private/no-store current-account assessment protected by authenticated session, exact approved HTTPS Origin and matching session-bound CSRF cookie. It reports verified/disabled status, password/Google method presence and session authentication age derived from the approved 12-hour absolute lifetime. It explicitly reports no factor enrollment, step-up, recovery codes or stored session-assurance provenance, with deterministic blockers. No MFA factor, secret, challenge or assurance authorization is implemented. Status: **IMPLEMENTED_NOT_VERIFIED**.

The exact pilot proposal is now documented at `backend/docs/mfa-step-up-policy.md` and recorded as BID-ADR-023 `Pending Approval`. It selects encrypted TOTP, ten one-time recovery codes, MFA-gated password/Google login, explicit session assurance, and recent TOTP step-up for package approval, submission confirmation and membership offboarding. The draft contract is `backend/api/openapi/drafts/mfa-step-up.json`. Preparation is **DESIGNED** only; no factor storage, challenge, assurance or governed-operation behavior changed.

## 13. Partial implementation evidence — 2026-10-18
The requesting user selected Go-owned email/password. The bounded control schema now stores users and Argon2id-v19 PHC strings only, with typed insert/login-record queries and control compatibility version 6 after additive email, verification-challenge and browser-session safeguards. A parameter-explicit Argon2id-v19 PHC component now supplies secure salts, strict bounded parsing, constant-time verification and rehash signaling without defaults. The user approved the pilot profile of 64 MiB / 3 iterations / parallelism 2, 16-byte salt, 32-byte key and 12–128 valid UTF-8 password bytes with no trimming/normalization/composition rules. `PilotPolicy` and `ValidateNew` encode that exact profile while zero/invalid policies still fail rather than default. The confirmed email value accepts strict printable-ASCII dot-atom mailboxes, preserves display case, lowercases the full lookup identity and performs no provider alias rewriting. The approved verification foundation generates 32 random bytes, stores only SHA-256, expires after 30 minutes, permits one active `EMAIL_VERIFY` challenge, invalidates prior challenges on resend and atomically consumes a valid unexpired token while setting `email_verified_at`. A route-independent use case and pgx/sqlc adapter now consume the token and append minimal `EmailVerified` audit evidence in one control transaction while concealing malformed/expired/replayed states. A route-independent credential authentication use case now mandates attempt-control hooks, exact-profile dummy PHC work for malformed/unknown identities, generic failures, verified/non-disabled/epoch checks and successful-login rehash signaling. Its generated-query reader uses a bounded read-only transaction. The approved session foundation uses domain-separated hashes for 32-byte session/CSRF values, 30-minute idle/12-hour absolute limits, rotation linkage, auth-epoch validation and revocation queries; cookie constants encode the approved `__Host-` attributes. The approved attempt policy is encoded as exact limits plus HMAC-SHA-256 identity/network scope derivation. Authentication now requires an atomic reservation/finish controller rather than a racy separate check/record pair, and fails closed for missing network scope or limiter failure. A login orchestration use case now requires successful authentication, performs mandatory profile rehash when signaled, generates session/CSRF values and requires one session-plus-security-audit commit before exposing cookie/bootstrap material. Concrete pgx/sqlc adapters now rehash outside the transaction with optimistic credential-version update, and atomically insert session plus minimal `UserLoggedIn` audit before returning secrets. Scripted DB-interface tests verify ordering, conflicts, audit minimization and rollback propagation. The Redis adapter now uses atomic reservation/finish Lua scripts, HMAC-only keys, one Cluster hash slot, single-use reservations and explicit verified-TLS/auth/timeouts/pool/no-retry configuration. Scripted runner tests do not constitute live Redis concurrency evidence. Current-session validation now rechecks verified/non-disabled/auth-epoch state and returns CSRF evidence through a redacted principal. Validation is read-only; idle touch is deliberately separate so rejected requests cannot extend a session. It deliberately provides no Redis deployment/secret reference, deployment trusted-proxy values, Fiber login/middleware handler, delivery provider, audited verification issuance, recovery, MFA or membership policy. Static migration/sqlc and centralized negative-scope tests are not ticket completion; status remains Blocked pending the original dependencies and live security evidence.

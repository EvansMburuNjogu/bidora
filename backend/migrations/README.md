# Bidora migration sets

Historical verification: **VERIFIED_TECHNICALLY at control 28, tenant-common 9 and Tenderpreneur 32 on isolated PostgreSQL 15.19**. Current source targets are control 53, tenant-common 9 and Tenderpreneur 34; the historical evidence below does not verify those later migrations live. Evidence includes original upgrades, fresh clean targets, exact runtime grants on clean targets, concurrent locked runners, bounded transactional fault rollback and restore-to-new-target equality. This is not deployment or application acceptance. PA-23's separately authorised loopback development rollout applied control migrations 35–37 to the existing `bidora_control_test` target, verified ledger/compatibility 37 and the bounded audit projection/grants, and registered exact SHA-256 entries in the checksum manifest. This is local PA-23 technical evidence, not SET-01 save acceptance, independent UAT or production approval.

There are three separate ordered sets:

1. `control` in the control database, with private Goose table `bidora_migrations.goose_control_version`
2. `tenant_common` in each tenant database, with private Goose table `bidora_migrations.goose_tenant_common_version`
3. `tenant_tenderpreneur` in a Tenderpreneur tenant database, with private Goose table `bidora_migrations.goose_tenderpreneur_version`

Never use one default Goose version table for multiple sets: each begins at version 1 and a shared ledger would incorrectly skip another set. In tenant databases, apply common first. A tenant of another type must not receive the Tenderpreneur extension automatically.

Pinned review tools:

```sh
go run github.com/pressly/goose/v3/cmd/goose@v3.29.0 -dir migrations/control validate
go run github.com/pressly/goose/v3/cmd/goose@v3.29.0 -dir migrations/tenant_common validate
go run github.com/pressly/goose/v3/cmd/goose@v3.29.0 -dir migrations/tenant_tenderpreneur validate
go run github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1 generate
go run github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1 diff
```

For a separately authorized database, build and invoke only the standalone `cmd/migrate` command with a verified-TLS dedicated migrator DSN supplied through `BIDORA_MIGRATION_DSN`. The command embeds the reviewed SQL, accepts only `control-auth:29`, `control:45`, `tenant-common:9` or `tenant-tenderpreneur:34`, uses the corresponding private ledger, and serializes concurrent processes with a database-and-set-scoped PostgreSQL session advisory lock. The reviewed private migration-ledger schema must already exist, and the DSN must set `search_path` to that schema followed by `pg_catalog` (the synthetic fixture uses `bidora_migrations,pg_catalog`). Never use writable `public` or rely on an ambient path:

```sh
BIDORA_MIGRATION_DSN="$CONTROL_MIGRATOR_DSN" ./bidora-migrate -set control -target 45
BIDORA_MIGRATION_DSN="$TENANT_MIGRATOR_DSN" ./bidora-migrate -set tenant-common -target 9
BIDORA_MIGRATION_DSN="$TENANT_MIGRATOR_DSN" ./bidora-migrate -set tenant-tenderpreneur -target 34
```

The variable references are illustrative only: never place a resolved DSN in shell history, arguments, repository, logs or evidence. Runtime startup never runs migrations.

After exact migrations succeed, the separately built `cmd/grant-runtime` command reconciles direct runtime schema/table/sequence privileges from the reviewed SQL query inventory. It requires both the dedicated migrator and runtime DSNs through environment-only channels, derives the runtime role from its authenticated connection, requires both connections to use verified TLS and the same database, and accepts only manifest version 1 for `control` or `tenant`. It requires exact control compatibility 45 or tenant compatibility 9/34, a login-only runtime role with no ownership, memberships or elevated attributes, database CONNECT without CREATE/TEMPORARY, and no PUBLIC application-table privileges. It revokes direct privileges in only the manifest schemas, grants schema USAGE and exact table-level SELECT/INSERT/UPDATE/DELETE operations, grants no sequence privilege, verifies the effective result, and commits atomically:

```sh
BIDORA_GRANT_DSN="$CONTROL_MIGRATOR_DSN" \
BIDORA_RUNTIME_DSN="$CONTROL_RUNTIME_DSN" \
  ./bidora-grant-runtime -plane control -manifest-version 1
BIDORA_GRANT_DSN="$TENANT_MIGRATOR_DSN" \
BIDORA_RUNTIME_DSN="$TENANT_RUNTIME_DSN" \
  ./bidora-grant-runtime -plane tenant -manifest-version 1
```

The API runtime credential must not own schemas/tables or receive CREATE/ALTER/DROP/TRUNCATE. `tests/runtimegrants` fails when reviewed query table operations and the manifest diverge; this does not replace operation-level integration, clean-target or deployment-role evidence. This repository does not invent environment role names or create roles.

## Migration contract

- PostgreSQL 15+; each Up migration sets 1-second lock and 5-second statement timeouts.
- UUIDs/timestamps are application-generated; migrations install no extensions.
- `control/00001` creates only provider-neutral Tenderpreneur tenant/cluster/database-assignment/schema-version routing and control compatibility metadata. `00002` adds append-only control audit and outbox facts and advances control schema to version 2. After the user selected Go-owned email/password, additive `00003` creates only users plus Argon2id PHC credentials and advances control schema to version 3. Confirmed email identity constraints are added by `00004`, advancing control schema to version 4; hypothetical pre-v4 rows must be reconciled before constraint validation/authentication. Approved hashed single-use email-verification challenges are added by `00005`, advancing control schema to version 5; no delivery provider or route is implied. Approved opaque browser-session/CSRF storage and lifetime constraints are added by `00006`, advancing control schema to version 6; cookie/Origin enforcement remains an HTTP integration gate; generated session queries include atomic current-session logout audit composition without storing cookie values. Confirmed current membership and explicit capability effects are added by `00007`, advancing control schema to version 7; role labels never authorize, active DENY wins and grant changes bump context generation. Approved Google external identities are added by `00008`, advancing control schema to version 8; only the stable provider subject binds an account, observed verified email is evidence rather than linking authority, and OAuth tokens are not stored. The approved fixed capture-contributor invitation is added by `00009`, advancing control schema to version 9 with SHA-256 token storage, 72-hour expiry, one active tenant/email invitation and immutable consume/invalidate history; it cannot grant administrator authority. Approved password-recovery challenge storage is added by `00010`, advancing control schema to version 10 with 32-byte SHA-256 token hashes, 30-minute expiry, resend invalidation and atomic single use. Recovery reset advances credential/auth-epoch state and revokes all sessions; public routes are conditionally composed with the approved fail-closed Redis limits and explicit SMTP configuration. The set does not create MFA, broader grant/last-admin workflows, databases or plaintext secrets.
- `tenant_common/00001` creates bounded audit/outbox/idempotency infrastructure; `00002` creates compatibility metadata; `00003` adds singleton organization identity plus non-authoritative local user projections; `00004` adds append-only payload-free event inbox receipts and advances common schema version to 4; `00005` additively requires immutable actor provenance on new outbox facts and advances common schema version to 5 / application generation 1. It intentionally does not create bids, requirements, verification, documents, approval or submission tables.

These migrations neither initiate payment nor grant paid entitlement. Migration execution and live race evidence for the new slices are deferred. Compatibility metadata does not authorize tenant routing and is not a migration ledger.
- `source_document_version_id` is a logical UUID until BID-DB-005 supplies the local document schema/FK. No endpoint may accept a non-null value before owner-port authorization/eligibility checks and the FK are reviewed and implemented.
- Audit, inbox receipts and source versions have mutation-rejecting triggers. Inbox uniqueness is `(consumer,event_id)` and has no automatic expiry; receipt and database effects must share one transaction. Outbox fact fields, including actor provenance, are immutable while delivery fields may progress. Actor IDs are provenance, never authorization.
- Idempotency has no automatic TTL under the approved capture contract. Key/request hashes are exactly 32 bytes; application authorization and tenant/actor/operation scope remain mandatory.
- Up migrations contain no destructive operation. Down sections are only for owned empty development databases. Production/data-bearing recovery is forward-fix or restore to a new target, never automatic Down.

`checksums.json` locks reviewed pre-release migration/schema/query/generation inputs, including the authorised control 35–37 SHA-256 entries. Before release, update it only with explicit review. After release, never edit an existing migration: add a new migration and update the release manifest. sqlc output under every `internal/*/persistence/sqlc` directory is generated, not hand-edited.

# Google OIDC identity foundation

Status: **VERIFIED_TECHNICALLY (persistence, claims, Redis transaction state, code exchange, JWT/JWKS verification and application-flow boundaries)** — 2026-10-18.

## Approved policy

Google authentication is additive to email/password. The account binding authority is the validated Google issuer plus stable `sub`; matching email is never authority to link accounts. ID-token acceptance requires the exact configured client audience, a supported Google issuer, signature verification by a future trusted-JWKS boundary, exact single-use transaction nonce, `email_verified=true`, valid times and the existing strict Bidora email syntax. A collision with an existing Bidora email returns a generic authentication failure until an already-authenticated user completes an explicit link operation with exact Origin, CSRF and recent password reauthentication. Google login creates no tenant membership or capability.

## Implemented bounded slice

- Control migration `00008_google_external_identities.sql` advances compatibility to version 8 and uniquely binds one Google subject to one user and one Google identity per user. `email_at_link` is evidence only.
- `internal/identity/googleoidc/claims.go` validates already signature-verified claims, audience, issuer, nonce, verified email and bounded token times. It does not decode or verify JWT signatures.
- `internal/identity/application/google_authenticate.go` orchestrates claim validation and takeover-safe identity resolution with generic public failures.
- `internal/identity/persistence/google_identity_store.go` signs in by stable subject, creates a verified zero-authority user only when the email is unused, records `GoogleUserRegistered`, and refuses email-only linking. Later provider email changes neither rebind nor overwrite the canonical Bidora email.
- `internal/identity/googleoidc/transaction.go` creates independent 32-byte state, nonce, PKCE verifier and browser-correlation values and derives an RFC 7636 S256 challenge. State is domain-hashed before it becomes a Redis key; only a domain-separated hash of the browser value enters Redis, for constant-time callback comparison by the future HTTP boundary.
- `internal/identity/oidcredis/transaction_store.go` stores only short-lived nonce/verifier/browser-binding-hash material under an explicit 1–15 minute TTL and atomically consumes it with deletion. Missing, expired, replayed and corrupt transactions fail generically; Redis errors fail closed. No default TTL exists.
- `internal/identity/googleoidc/authorization.go` builds only Google's fixed authorization endpoint with exact configured client/callback values, `openid email`, independent state/nonce and S256 PKCE parameters.
- `internal/identity/application/google_oidc_flow.go` persists a transaction before exposing its redirect, then atomically consumes state before callback work, verifies the browser-correlation value before code exchange, exchanges with the stored verifier, verifies the signed token with the stored nonce and resolves the stable subject. Its result is an authenticated Bidora identity. `internal/identity/application/google_login.go` then uses the provider-neutral session issuer shared with password login, so session/CSRF secrets are returned only after the session and a method-qualified `UserLoggedIn` audit commit atomically.
- `internal/identity/googleoidc/exchange.go` posts an authorization code, exact configured HTTPS callback URI and the stored PKCE verifier to Google's fixed token endpoint through a single-request `RoundTripper`. Configuration is explicit and redacted; redirects are not followed by this boundary. Responses are bounded and duplicate-key checked, and only the ID token is returned—access/refresh tokens are discarded.
- `internal/identity/googleoidc/token.go` accepts only bounded three-segment RS256 JWTs, rejects duplicate JSON members, resolves the exact `kid`, verifies the signature before payload interpretation, and then applies the approved issuer/audience/nonce/verified-email/time policy.
- `internal/identity/googleoidc/transport.go` provides the production transport boundary: explicit cloned trust roots, TLS 1.2+, bounded dial/handshake/header/connection settings, no ambient proxy, no automatic decompression and exact method/URL allowlisting for only the JWKS and token endpoints. It implements one `RoundTrip` and therefore does not follow redirects.
- `internal/identity/googleoidc/jwks.go` requests only Google's fixed HTTPS JWKS endpoint, accepts bounded JSON RSA/RS256/signing keys of 2048–4096 bits, requires a source `max-age`, caps cache life at six hours, refreshes for rotation, rate-limits unknown-`kid` refreshes and fails closed when an expired/required refresh fails. Unknown keys produce generic invalid-token behavior rather than dependency details.
- No Google access or refresh token is stored.

Live synthetic PostgreSQL evidence covers migration 8, first Google signup, stable-subject sign-in after a provider email change, zero membership creation and denial of a second subject claiming the same email. Live TLS Redis evidence verifies one successful consume among 24 concurrent callback attempts, replay denial and reuse of the deleted state key only through a newly created transaction.

## Explicit exclusions and remaining gates

This slice does not activate HTTP routes or compose Google into `cmd/pilot-api`. External-Google acceptance and deployment-owned trust-root/timeout/client/callback/redirect values and transport lifecycle, Google client credentials, external-Google link acceptance, HTTP cookie issuance, logout interaction and hosted-domain policy remain required. Environment-loaded `cmd/pilot-api` configuration now requires explicit Google credentials, callback, fixed redirects, TTL and roots; `pilot.Build` composes the transport, Redis state, verifier, PostgreSQL identity/session adapters and registers Google signup/sign-in start/callback routes and authenticated Google-link start/callback routes behind session/CSRF middleware, with a separate exact link callback and fixed link redirects. A live local pilot bootstrap verifies the configured start route and Redis correlation cookie without contacting Google. The user proceeded with the stricter linking interpretation: every link initiation must perform a fresh password authentication for the same currently authenticated user and auth epoch; no reusable recent-authentication window is created. `internal/identity/application/google_link_reauthenticate.go` implements this boundary through the existing fail-closed password/attempt controls and mandatory profile rehash. A matching email still grants no linking authority. Redis transaction material is now explicitly `SIGN_IN` or `LINK`; link material contains only a domain-separated hash binding the current user ID, session ID, auth epoch and freshly verified credential version. Normal sign-in rejects link-purpose state before browser comparison or provider exchange, and link binding comparisons are constant-time. `internal/identity/application/google_link.go` and its PostgreSQL committer now atomically lock the current verified password identity/session/credential version, reject either existing subject or existing user-provider bindings, insert the Google subject, increment auth epoch, revoke all old sessions, create a replacement session linked to the current session, and append `GoogleIdentityLinked` plus method-qualified `UserLoggedIn` audits. Secrets are returned only after commit. Live PostgreSQL evidence verifies the rotation, zero membership and stale-proof denial. `internal/identity/application/google_link_flow.go` now composes fresh password proof with `LINK` state creation, then on callback consumes state, validates the exact current user/session/auth epoch and browser binding before exchange, verifies the token with the stored nonce, and invokes the atomic link committer with the stored credential version. Principal swaps stop before provider exchange. A composed live synthetic link test now traverses session/CSRF middleware, Redis attempt and purpose-bound state controls, local RS256/JWKS exchange, PostgreSQL link persistence and cookie rotation; it verifies auth-epoch advancement, old-session revocation, replacement-session lineage and replay rejection before another provider exchange. The linking HTTP boundary now provides authenticated/CSRF-protected strict `POST /v1/auth/google/link/start` with fresh email/password proof and trusted-network scope, plus current-session `GET /v1/auth/google/link/callback`; it reuses the host-only correlation cookie, fixed generic redirects and replacement session cookies only after atomic rotation. See `api/openapi/drafts/google-link.json`. The approved unregistered HTTP boundary uses `POST /v1/auth/google/start` with exact Origin and `GET /v1/auth/google/callback` with exact state/code, a `__Host-bidora_google_oidc` Secure/HttpOnly/SameSite=Lax correlation cookie, fixed success/failure redirects, no-referrer/no-store responses, approved session cookies only after commit and unconditional correlation-cookie clearing. See `api/openapi/drafts/google-auth.json`. JWKS tests use deterministic in-memory HTTP responses and locally generated RSA keys. Transport tests prove rejection before I/O and safe cancellation at the allowlisted network boundary. A composed synthetic HTTP acceptance test now drives the real handlers, TLS Redis transaction store, signed RS256 token/JWKS verifier, PostgreSQL identity resolver and session/audit commit; it verifies zero membership and callback replay denial before a second token exchange. The Google endpoint is replaced by an in-memory fixed-endpoint transport, so no external Google network call or deployment readiness is claimed. Redis/JWKS failures must fail closed. A callback must not pass unverified decoded claims to this foundation.

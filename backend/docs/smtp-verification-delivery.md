# SMTP email-verification delivery

Status: adapter protocol-tested and composed into configurable `cmd/pilot-api` password registration; no SMTP vendor is configured and no deployment/provider acceptance is claimed.

The user selected provider-neutral SMTP for pilot verification email. `internal/identity/deliverysmtp` requires an explicit host/port, ACL username/password, validated sender mailbox, trust roots, TLS server name and bounded timeout. It refuses plaintext delivery: the server must advertise STARTTLS, complete verified TLS 1.2 or newer, and advertise AUTH PLAIN after TLS before credentials are sent.

Messages are minimal UTF-8 plain text containing the verification token and UTC expiry. They include no user ID, tenant ID, membership, captured opportunity data or tracking content. The adapter does not log configuration, recipient or token values, and its surfaced error is always `email_delivery_unavailable` while preserving a wrapped cause for trusted diagnostics.

Issuance commits the hashed challenge and audit before calling delivery. Therefore timeout or ambiguous SMTP failure does not pretend the challenge rolled back; resend creates a fresh token and atomically invalidates the prior active challenge.

Environment-loaded pilot composition now requires explicit SMTP values and registers `POST /v1/auth/register` behind readiness. Live synthetic composition tests use real TLS Redis and PostgreSQL. One traverses the full pilot registration route through authenticated STARTTLS and verifies the minimal verification message, generic verified-email-only login denial before token consumption, token consumption, password login and session bootstrap, denial of tenant capture with no persisted source row, audited logout with cookie clearing and old-session rejection, identity/password/challenge/audit persistence, zero membership and generic duplicate acceptance without a second challenge or success audit. Another deliberately targets an unavailable SMTP endpoint and proves that the already-committed unverified identity/password and hashed active challenge remain durable while the response stays generic `202`. Existing adapter protocol tests also prove plaintext downgrade rejection. These combined tests do not prove a real sender domain or external provider.

The adapter deliberately does not choose an SMTP vendor, discover ambient mail settings, accept unverified TLS, support unauthenticated relays, render HTML, construct a frontend verification URL, add tracking, manage DKIM/SPF/DMARC, process bounces, retry in-process or provide a durable delivery queue. Deployment SMTP values, sender-domain controls, retry/queue policy, bounce handling and operational monitoring remain separate gates. The registration and public verification-consumption HTTP contracts are implemented and composed. Verification uses `POST /v1/auth/verify-email` with the token only in a strict JSON body, exact approved Origin, generic invalid/expired/consumed behavior, no session cookies and no tenant authority. No resend HTTP route is selected.

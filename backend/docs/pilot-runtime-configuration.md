# External Tender Pilot runtime configuration contract

Status: implemented-not-verified after the MinIO upload increment; not activated by `cmd/api` and not a production configuration.

`internal/pilot.LoadDeploymentConfig` accepts only explicit values supplied by a process owner. It does not read environment variables itself, resolve secret references, discover libpq settings, run migrations, open pools/listeners or mark readiness. Callers must provide `os.Getenv` and a bounded file reader deliberately.

Required global keys:

- `BIDORA_PROFILE=external-tender-pilot`
- `BIDORA_ENV`: one of `local`, `test`, `staging`, `production`
- `BIDORA_HTTP_ADDR`: explicit IP literal and non-zero port
- `BIDORA_ALLOWED_ORIGINS`: comma-separated exact HTTPS Origins
- `BIDORA_TRUSTED_PROXY_CIDRS`: comma-separated canonical CIDRs; omission and `none` are rejected
- `BIDORA_ATTEMPT_HMAC_SECRET_B64`: unpadded base64 encoding of exactly 32 random bytes
- `BIDORA_DUMMY_PASSWORD_PHC`: an Argon2id PHC string matching the approved pilot profile
- `BIDORA_REDIS_ADDRESS`, `BIDORA_REDIS_USERNAME`, `BIDORA_REDIS_PASSWORD`, `BIDORA_REDIS_CA_FILE`, `BIDORA_REDIS_TLS_SERVER_NAME`, `BIDORA_REDIS_PREFIX`
- `BIDORA_GOOGLE_ENABLED`: explicit `true` or `false`; `false` leaves all Google routes absent without disabling password authentication/registration
- Google client credentials and enabled/signup/domain policy are managed in Settings → Google Login & Signup, not environment variables. Legacy `BIDORA_GOOGLE_CLIENT_ID` / `BIDORA_GOOGLE_CLIENT_SECRET` inputs are ignored; nothing is imported or activated automatically.
- When `BIDORA_GOOGLE_ENABLED=true`, `BIDORA_GOOGLE_CALLBACK_URL`: exact public HTTPS callback registered with Google; no query, fragment or userinfo
- When `BIDORA_GOOGLE_ENABLED=true`, `BIDORA_GOOGLE_SUCCESS_REDIRECT`, `BIDORA_GOOGLE_FAILURE_REDIRECT`: distinct fixed HTTPS application destinations without query/fragment/userinfo
- When `BIDORA_GOOGLE_ENABLED=true`, `BIDORA_GOOGLE_LINK_CALLBACK_URL`: exact separate HTTPS callback registered for authenticated linking
- When `BIDORA_GOOGLE_ENABLED=true`, `BIDORA_GOOGLE_LINK_SUCCESS_REDIRECT`, `BIDORA_GOOGLE_LINK_FAILURE_REDIRECT`: distinct fixed HTTPS security-settings destinations
- When `BIDORA_GOOGLE_ENABLED=true`, `BIDORA_GOOGLE_TRANSACTION_TTL_SECONDS`: explicit integer from 60 through 900
- When `BIDORA_GOOGLE_ENABLED=true`, `BIDORA_GOOGLE_CA_FILE`: explicit PEM trust roots for the allowlisted Google JWKS/token transport
- `BIDORA_SMTP_VAULT_KEY_FILE`: optional private file containing one base64-encoded 32-byte AES-256-GCM key; enables database-managed SMTP mutation/delivery and separately AAD-scoped Google secret encryption. Registration verification, verification resend, recovery, login codes (including optional Platform email-OTP), invitations and template tests use the active Platform Admin SMTP revision. No deployment SMTP fallback is used; without an active revision delivery is unavailable. `BIDORA_PLATFORM_EMAIL_OTP=true` retains the additional Platform login-code gate but now requires this managed revision. Legacy `BIDORA_PLATFORM_LOGIN_SMTP_*` settings are rejected; remove them before deploying a runtime with the gate enabled.
- `BIDORA_SMTP_VAULT_KEY_VERSION`: positive version for the configured vault key; the key itself is never stored in PostgreSQL
- `BIDORA_NOTIFICATION_FINGERPRINT_KEY_FILE` / `BIDORA_NOTIFICATION_FINGERPRINT_KEY_VERSION`: optional paired inputs for durable verification/recovery notification attempts; private file contains a base64-encoded 32-byte key, version is a positive int32. Requires managed SMTP. Composition rejects reuse of SMTP-vault or login HMAC keys. No key is generated implicitly. When configured, verification/recovery use exact-active SMTP plus the existing notification recorder after the challenge commits; recipients/content are fingerprinted, not persisted by the ledger. SMTP handoff is not delivery confirmation. Evidence-aware Platform administrator communications and template self-tests also use the recorder. Login-code/tenant-invitation adapters consume managed templates but do not gain ledger evidence merely from enabling this key. The local `cmd/identity-api` accepts equivalent explicit `BIDORA_LOCAL_NOTIFICATION_FINGERPRINT_KEY_B64` / `BIDORA_LOCAL_NOTIFICATION_FINGERPRINT_KEY_VERSION` variables. Leaving both unset preserves existing delivery behavior, not a claim of recorded attempts.
- Legacy `BIDORA_SMTP_HOST`/credential/sender inputs are no longer consumed by runtime composition; SMTP configuration is governed from Platform Administration
- `BIDORA_MINIO_ENDPOINT`, `BIDORA_MINIO_BUCKET`, `BIDORA_MINIO_ACCESS_KEY`, `BIDORA_MINIO_SECRET_KEY`
- `BIDORA_MINIO_TLS_SERVER_NAME`, `BIDORA_MINIO_CA_FILE`: mandatory verified HTTPS identity and explicit PEM roots
- `BIDORA_MINIO_TIMEOUT_SECONDS`: explicit integer from 1 through 30
- `BIDORA_CLAMAV_SOCKET`: absolute local Unix-socket path; document bytes are never sent to an unverified network scanner
- `BIDORA_CLAMAV_TIMEOUT_SECONDS`: integer from 1 through 120; `BIDORA_CLAMAV_CHUNK_BYTES`: integer from 4096 through 1048576
- `BIDORA_OPENAI_API_KEY`: deployment-owned secret; never persisted or logged
- `BIDORA_OPENAI_MODEL`: explicit model identifier with no fallback default
- `BIDORA_OPENAI_CA_FILE`: explicit PEM trust roots; `BIDORA_OPENAI_TIMEOUT_SECONDS`: integer from 10 through 900
- `BIDORA_CONTROL_HOST`, `BIDORA_CONTROL_PORT`, `BIDORA_CONTROL_DATABASE`, `BIDORA_CONTROL_USER`, `BIDORA_CONTROL_PASSWORD`, `BIDORA_CONTROL_CA_FILE`
- `BIDORA_TENANT_COUNT`: integer from 1 through 100

For each zero-based tenant index `N`, all of these are required:

- `BIDORA_TENANT_N_ID`
- `BIDORA_TENANT_N_CLUSTER_ID`
- `BIDORA_TENANT_N_ASSIGNMENT_GENERATION`
- `BIDORA_TENANT_N_DATABASE_NAME`
- `BIDORA_TENANT_N_SECRET_REF`
- `BIDORA_TENANT_N_ENDPOINT_REF`
- `BIDORA_TENANT_N_REGION`
- `BIDORA_TENANT_N_POSTGRES_HOST`, `..._PORT`, `..._DATABASE`, `..._USER`, `..._PASSWORD`, `..._CA_FILE`

The indexed PostgreSQL database must equal the registered assignment database name. Control and tenant targets cannot resolve to the same host/port/database tuple; tenant IDs and targets cannot be duplicated. PostgreSQL uses fixed bounded pool/time settings, verified TLS and SCRAM through the existing portable adapter. Redis uses verified TLS, an explicit ACL username and bounded timeouts. SMTP is optional at startup. With a vault key configured, Platform Administration can store encrypted credentials/trust roots and govern test/activation; without an active resolvable profile, ordinary login sends no email code and remains AAL1 while email ownership verification and recovery remain unavailable. When the database vault is composed, the runtime registers `POST /v1/auth/password`, `POST /v1/auth/register`, `POST /v1/auth/verify-email`, `POST /v1/shared/invitations`, and `POST /v1/shared/invitations/accept`, manager-authorized paginated `GET /v1/shared/invitations`, bounded `DELETE /v1/shared/invitations/{invitation_id}`, `GET /v1/me/memberships`, manager-authorized `GET /v1/shared/memberships`, and bounded `DELETE /v1/shared/memberships/{membership_id}` behind readiness. Password change uses current session/CSRF, fresh fail-closed password proof, atomic credential/auth-epoch advancement, all-session revocation and one replacement session; wrong proof leaves identity state unchanged. It composes strict request binding, privacy-safe Redis registration limits, transactional unverified password identity creation, hashed single-use verification challenge issuance, SMTP delivery and atomic verification consumption. Registration never creates membership or tenant authority. Delivery runs only after the challenge transaction commits; an ambiguous delivery failure remains a generic `202` and leaves the challenge eligible for approved resend handling. Verification accepts the token only in a strict JSON body under an exact approved Origin, emits no cookies or session, maps unknown/expired/consumed tokens to one generic failure and creates no membership or capability. Invitation issue/acceptance additionally require the current browser session and CSRF proof; issuance rechecks the selected tenant/context and deny-first management capability, while acceptance binds the token to the current verified matching email and grants only the fixed capture capability. Invitation delivery reuses the explicit authenticated-STARTTLS transport after the issue transaction commits. The current-user membership directory returns only current ACTIVE-tenant memberships and deny-filtered explicit capabilities; role labels and tenant IDs remain non-authoritative. The pending-invitation directory is bounded to 100 rows per page, uses a stable created-time/ID cursor, filters expired/invalidated/consumed rows, and never returns token material. Pending cancellation invalidates one fixed-role invitation atomically with audit/outbox evidence and conceals inaccessible, consumed, expired, invalidated and replayed targets. The managed directory exposes only fixed capture contributors and their display emails after deny-first manager authorization. Contributor revocation requires control-runtime `UPDATE` on `tenancy.memberships` and `tenancy.role_grants`; its target predicate excludes memberships with administrator, manager, DENY, or any other active grant.

MinIO is mandatory for the composed pilot upload routes. The runtime accepts only verified TLS, server-owned bucket/key selection and static deployment credentials hidden behind the storage port. Readiness verifies that the bucket exists, has versioning enabled and has no bucket policy (access must come only from deployment-owned MinIO identity policy); it does not create buckets, enable versioning or alter provider policy. `POST /v1/tenderpreneur/opportunities/{opportunity_id}/documents/uploads` accepts only declared PDF/DOCX objects through ten-minute checksum-, media-type- and exact-size-bound multipart POST instructions. Completion binds the exact MinIO version, size, media type and SHA-256, records an immutable `QUARANTINED` document version, queues malware scanning and creates the AI job in `WAITING_FOR_CLEAN`. No current route serves quarantined bytes or advances analysis.

The composed process also runs a bounded tenant-by-tenant document worker. It streams the exact immutable MinIO version to local ClamAV without holding a SQL transaction. `CLEAN` atomically releases the waiting analysis job; malware atomically marks the version `REJECTED` and cancels analysis. Scanner/dependency failure leaves the version `QUARANTINED` and fails the processing loop visibly rather than treating it as clean. Only a currently authorized uploader's CLEAN version reaches the exact OpenAI Responses endpoint. The request uses `store:false`, streams the file without a local full-file buffer, requires strict structured output, rejects duplicate/unknown response fields, and stores only bounded `PROPOSED_UNVERIFIED` requirement suggestions with quote/location citations. The API key is environment-supplied for this MVP; a platform-admin secret store is not implemented. Bid evidence reuses the private MinIO and ClamAV boundaries through `POST /v1/tenderpreneur/bids/{bid_id}/evidence/uploads` and its completion route, but creates no AI job. Only the upload owner can complete/read its scan job, with either current document-upload or requirement-management authority as appropriate. `POST .../requirements/{requirement_id}/satisfy` accepts only an exact CLEAN BID_EVIDENCE version owned by the same BID workspace and commits immutable evidence, requirement/workspace versions, audit, outbox and idempotency atomically. The review boundary exposes bounded `GET .../ai-requirements` plus idempotent `POST .../{suggestion_id}/accept|reject` routes. Acceptance requires the current requirement-management capability and matching clean document/opportunity/verified-source/BID-workspace versions, then creates an authoritative `OPEN` requirement without mutating the model proposal. Rejection requires a human note. Technical response routes provide one bounded plain-text section per requirement, immutable revisions, same-requirement evidence links and optimistic workspace/section versions under `tenderpreneur.bid.response.edit`; no financial fields exist in these DTOs. The gap-review read reports deterministic missing-response, unsatisfied, unassigned, overdue and decision blockers without invoking AI or claiming approval.

TP-F09 additionally requires an existing deployment-owned NATS JetStream stream `BIDORA_TENANT_AI_ENTITLEMENT` and durable consumer `control-commercial-ai-reservation-v1` on subject `bidora.v1.tenant.ai_entitlement.reserve_requested`. Configure `BIDORA_NATS_URL` as a TLS URL without userinfo, a mode-private `BIDORA_NATS_CREDENTIALS_FILE`, explicit CA file/server name and 1–30 second connect timeout. Runtime validates but never creates or edits the stream/consumer. `BIDORA_DOCUMENT_MEASURER_PATH` must be an absolute executable regular file built from `cmd/document-measurer`; no ambient PATH lookup is used. Entitlement-bound PDF response drafting additionally requires `BIDORA_PDFTOTEXT_PATH` to name an explicit executable regular Poppler `pdftotext` binary. Runtime never searches `PATH`, installs Poppler or invokes it during configuration; each use has an empty environment, no shell, fixed UTF-8/stdin/stdout arguments, exact input hash/size checks, bounded output and the approved parser deadline. DOCX character counting remains inside the isolated document measurer. These values contain no permission to start or provision NATS, MinIO, ClamAV or OpenAI.

Google deployment preparation is explicit: `BIDORA_GOOGLE_ENABLED=false` leaves OIDC routes absent without disabling password authentication; configuration/status endpoints remain available. When true, fixed callbacks/redirects, roots and TTL are validated, but credentials and policy come only from managed encrypted revisions. The identity-only command prepares this transport when an explicit callback is configured. Saving/connecting Google requires current context, recent Owner TOTP and a verified password/TOTP Owner fallback. Every revision invalidates in-flight login/link transactions; commit-time head fencing rechecks enabled/revision/exact email domain. Signup disabled permits existing linked subjects, not new users. Matching email alone never links or grants administrator access. Password authentication and mandatory MFA stay unchanged. `GET /v1/auth/google/status` exposes only Origin-bound availability flags. The connection test probes Google JWKS; `JWKS_REACHABLE_CREDENTIALS_UNVERIFIED` is deliberately not credential or sign-in verification. Actual OIDC acceptance remains BID-MVP-05.

Managed notification templates/preferences require control schema 39 and its exact runtime grants. Nine existing EMAIL types are supported; recovery/security/required invitations cannot be disabled. Only reminder preferences are optional; this does not create reminder scheduling or invent billing/support delivery. Template edits preserve immutable revisions and audit/outbox/idempotency; previews use synthetic values and escaped content. Runtime delivery adapters read current templates and shared branding, fail closed on missing required values, and record the actual template revision where notification evidence is configured. Fingerprints bind stable rendered subject/text/HTML, not random MIME boundaries/dates. Self-tests require recent Owner TOTP, use only the administrator's server-resolved verified email and exact-active SMTP, and preserve existing attempt evidence; SMTP acceptance is not recipient delivery. Unknown/pending results are never automatically resent. Migration 39 requires schema-compatible code or forward repair, never automatic down migration. Provider activation, real sends and production acceptance are separate operations.

Configuration formatting is wholly redacted. Validation errors contain stable categories rather than submitted values. Raw credentials, HMAC material, PHC values and certificate bytes must not be logged. `pilot.Open` consumes a validated configuration, lazily opens only those pools, probes Redis and every PostgreSQL target, verifies control and tenant schema compatibility plus MinIO bucket versioning, and marks readiness only after all checks pass. Any internal dependency/bootstrap failure leaves readiness false and closes created dependencies, including Google transport idle connections. Startup validates but does not connect to SMTP and therefore does not claim sender/provider deliverability. Startup does not call Google or claim provider availability; JWKS/token failures remain fail-closed at request time until deployment acceptance supplies external evidence. `Deployment.Shutdown` drains readiness before bounded HTTP, Redis and PostgreSQL cleanup. `cmd/pilot-api` supplies listener startup and SIGINT/SIGTERM handling through `pilot.Run`/`pilot.Serve`; no command is started by tests or builds. Deployment owners still supply secrets, certificate rotation, approved proxy values, process supervision and production acceptance.

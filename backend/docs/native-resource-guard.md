## Resume-safe credential reconstruction

`localbootstrap.RestoreCredential(password []byte)` accepts only the canonical 43-byte ASCII base64url password format generated by this fixture. It copies the supplied password and derives a PostgreSQL-format SCRAM-SHA-256 verifier using a fresh random salt. It does **not** change the password, rewrite the private file, activate a role or advance a checkpoint.

Call it only after `Store.ReadCredential` has checked the owned private store. Encoding validity alone does not prove provenance or entropy. Restored values retain existing credential/SQL formatting and JSON redaction. Explicit password/SQL accessors remain sensitive, and Go memory zeroization is not guaranteed.

A fresh salt means the verifier text changes while the password does not. A future executor must not interpret differing verifier strings as a reason to reset an existing role. Reconcile role attributes/grants and actual authentication before completing a pending activation; do not blindly repeat ALTER ROLE. No server authentication or SQL execution was performed here.

Tests independently recompute SCRAM keys, reject malformed/noncanonical/oversized inputs, verify copy/redaction behavior, and reopen an actual temporary private store to prove restoration leaves its password and pending checkpoint unchanged.

## Resource-policy API

`backend/internal/localbudget/guard.go` evaluates observations supplied by a future trusted collector:

- `NewGuard(Identity{PID, StartedAt})`: require an explicit process identity; PID alone is not sufficient.
- `Observe(now, Sample)`: validate identity, completeness, timestamps, cumulative CPU and resource totals, then return a decision.
- `Check(now)`: fail if observations are missing or stale, even when the collector has stopped producing samples.
- `MeasurementFailure()`: latch a safe stop decision without receiving/logging raw collector errors.

A stop decision is terminal for that guard. Later healthy samples cannot reset it. There is no limit-increase/reset API. Any new run must be separately and explicitly owned; supervisors must not recreate guards to evade a stop.

## Implemented conservative thresholds

These are implementation defaults within the approved monitored 2 CPU / 2 GiB RAM / 10 GiB experiment budget, **not hard OS quotas**:

| Condition | Decision |
|---|---|
| RSS at or above 1.5 GiB | Stop requested immediately on observation |
| Total experiment storage at or above 8 GiB | Stop requested immediately on observation |
| Aggregate CPU at or above 180% for 10 continuous sampled seconds | Stop requested; a below-threshold interval resets the high-CPU streak |
| Sample age or gap over 2 seconds | Stop requested |
| Missing sample, incomplete measurement or explicit collector failure | Stop requested |
| PID/birth identity change, time regression, future/replayed timestamp or CPU-counter regression | Stop requested |

Intended collector cadence: **one second**. CPU uses cumulative process-tree CPU-time deltas divided by sample-time deltas; 200% means two cores. Integer comparison uses a rounded-up 9/5 threshold without multiplying an unbounded CPU counter. The first observation establishes a CPU baseline; it is not CPU-compliance evidence. RSS/storage are checked on that observation.

The collector must aggregate all relevant owned descendants and retain accounting for exited descendants. Storage must include retained source/build/install/cache/profile artifacts plus fixture data/WAL/logs, not table size alone. A sample's `Complete` field is an assertion by trusted code, not proof of correct collection. Process identity also requires actual kernel validation, not user-selected PID/timestamp values.

## What is not implemented or demonstrated

- No native OS collector, filesystem accounting walk, sampling timer or stop supervisor is wired up.
- No process ownership/startup/shutdown action is performed by the guard. `Decision.Stop` is a request, not proof a process stopped.
- A supervisor must schedule `Check` even when collection hangs, and enforce bounded safe shutdown against the validated owned process. Merely calling Observe occasionally is not a monitor.
- Sampling can miss peaks or short-lived descendants; shared RSS can be conservatively double-counted. No claim of zero overshoot or complete hostile-host isolation is made.
- Real resource measurement/stop behavior, PostgreSQL SCRAM login, role denial and persistence remain untested and require separate live-execution authorization/acceptance.

The implementation is synchronized for concurrent calls; guard/identity state is not global. Zero-value guards fail closed. No frontend/API/business-policy or AI usage-ledger behavior changes.
